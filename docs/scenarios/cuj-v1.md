# cuj-v1: critical user journeys over the nine sites

`cuj-v1` is a scenario and the corpus of tasks written for it. The tasks are
the errands people send an agent on: find the one that fits, price it, book
it, change it, cancel it, send it back, act on their own account, carry one
booking through a conversation, plan an outing over several sites. Each task
belongs to one of ten **focus areas**, has one of four **levels**, and may run
over several prompts of one conversation (**steps**). A step is checked by the
reply it gets (`json`) or by what the sites hold afterwards (`state`), and
every step has its own judge criteria (`rubric`).

## The scenario

```
POST /api/workspaces        {"scenario":"cuj-v1","seed":4242}   → urls for the nine sites and the inbox
```

The workspace has the nine sites of `webmcp-v1` (hotels, flights, dining,
pizza, cinema, sports, homes, clinic, events; see the README's *Sites from
webmcp-tools*) and the inbox, with the same rows as a `webmcp-v1` workspace
of the same seed. It adds the **accounts** some of the sites' people already
have: on each site, four of the people its rows have something for (a
booking, an order, a viewing, a prescription, a place in the staff
directory), signed up and verified, each with a password a person can type.
They are drawn from a stream of their own (`substream(seed, "cuj-v1:accounts:<app>")`),
so the same seed gives the same accounts, and nothing else in the rows moves.
A task that asks someone to act on their own account says who they are and
gives their password; a task that asks for a new account names an email no
account has. The warehouse, the helpdesk and the vault are not part of it.

On every site a write needs someone signed in, through every door (the
README's *The same sign-in on every door*): signing up mails a code to the
workspace inbox, which has to be read there. Any account will do for a write
unless the task is about acting as a particular person.

The scenario's mailboxes are private (`mailboxes: "private"`): everyone its
rows already hold, on any of the nine sites (a booking's guest, a patient, an
event's organiser or guest, the owner of an account), has a mailbox of their
own, which the inbox never shows. Signing up in the name of someone who
already exists in the workspace therefore cannot be finished: their code goes
to their own mailbox. The account a write needs is signed up with an address
no row holds (one the agent makes up, or the new person's a task names),
whose code is in the inbox as before; a task about acting as one of the
workspace's people gives the password of the account they already have.

## The files

All generated by `node tools/intent-corpus.mjs` from the scenario's rows and
the templates in `tools/intent-corpus/cuj/templates/` (one module per focus
area), never edited by hand; `node tools/intent-corpus.mjs --check` fails when
the committed files are not the tool's output.

| file | what |
| --- | --- |
| `compose/specs/cuj-corpus.json` | one record per task, with its answer key (below): what a platform that grades the answers itself imports |
| `compose/specs/cuj-tasks.json` | the same records without `key`: what can be shown to anyone |
| `compose/specs/cuj-tasks.md` | how every task was derived, template by template, with the counts per area and level |
| `compose/specs/cuj-<id>.json` | the verifier's answer key for one task, served by id. A task whose every step is answered in a reply has none: the verifier has nothing of it to check (it would answer 422 `NO_STATE_STEP`) |

## The record

```jsonc
{
  "id": "cuj-change-party-area-01",        // cuj-<template>-NN: unique, stable at one seed
  "area": "change-it",                      // one of the ten focus areas
  "level": "medium",                        // easy | medium | hard | impossible
  "veryHard": false,                        // true only with level "hard"
  "apps": ["dining"],                       // the sites the task touches, in the order it meets them (1 to 4)
  "app": "dining",                          // apps[0]
  "surfaces": ["pages", "tools"],           // the doors that can do it
  "intent": "…",                            // step 1's prompt
  "rubric": ["…", "…", "…"],               // step 1's judge criteria (2 to 6)
  "steps": [                                // the follow-up prompts, 0 to 7; step 2 is steps[0]
    { "intent": "…", "rubric": ["…"], "kind": "state" }
  ],
  "kind": "state",                          // step 1's check: "json" | "state"
  "stateChecked": true,                     // present, and true, when at least one step's oracle is a state check; absent otherwise
  "summary": "…",                           // what a correct outcome is, in a sentence
  "key": {                                  // the answer key: keep it from the agent
    "blind": false,
    "oracle": { "kind": "state", "checks": [ … ] },   // step 1's
    "steps": [ { "oracle": { "kind": "json", "expect": { "total": 910 } } } ]   // one per follow-up, in order
  }
}
```

- **`intent`** is the whole instruction about the errand: plain language, no
  address of any site, nothing about how it is checked. Nothing is appended to
  it. A prompt names its site by what it is ("the restaurant reservation
  site"), and the people it books for by name and email.
- **`steps`** are further prompts in the same conversation. A later step's
  prompt always carries a fact the earlier ones did not (the new time, the
  room to fall back on, the guest who cannot come), so it cannot be done early.
- **`kind`** and each step's `kind` say how that step is checked. A `json`
  step's prompt asks for an answer as JSON with named fields; its key's
  `expect` holds the value of each, with a tolerance for money. A `state` step
  is checked by the verifier (below).
- **`stateChecked`** is there, and `true`, exactly when step 1 or a follow-up
  has a state check; a task answered in replies alone carries no such field.
  It is the one field to test before calling the verifier for a task.
- **`key`** is `cuj-<id>.json` without its `id`, when that file exists: the
  same oracle and steps the verifier reads.

## The focus areas

| key | the user wants | shape | sites |
| --- | --- | --- | --- |
| `find-the-fit` | the only option that meets several requirements | answer | all nine |
| `price-it` | the full cost of a named choice, fees and extras included | answer | hotels, flights, pizza, clinic, sports, cinema |
| `book-it` | a named booking or order made for a new customer | change | all nine |
| `book-the-best` | the cheapest or earliest option that fits, found and then booked | change | hotels, flights, cinema, dining, homes |
| `change-it` | one existing booking changed, and nothing else | change | dining, pizza, events |
| `cancel-it` | one booking cancelled, the customer's others left alone | change | all nine |
| `return-or-repeat` | a return, a reorder or a refill, inside the site's rules | change | sports, clinic |
| `act-as-yourself` | to sign up with an emailed code, or sign in, and act on their own account | change | all nine, with the inbox |
| `carry-a-conversation` | to book, then change it, then undo part of it, in one conversation | multistep | pizza, dining, events, hotels |
| `plan-across-sites` | one outing or trip over two or three sites, under a shared schedule or budget | multistep | flights, hotels, dining, cinema, events |

## Levels

A level is never written on a task. A template declares the task's countable
properties, `levelOf` in `tools/intent-corpus/cuj/levels.mjs` derives the
level from them, and the integrity tool measures them again on the task's
reference solution, against live sites, and refuses a task whose measurement
gives another level.

| level | defined by |
| --- | --- |
| easy | One site. The target is named in the prompt. One read or one write. No rule changes the outcome. |
| medium | One site (one per step). The target must be found by two or three constraints, or a rule changes the outcome (a fee, a party size). One write. |
| hard | A tempting option that fails one constraint; or three to five steps; or a sign-up with an emailed code before the task can start. |
| very hard (a flagged part of hard) | Two or more sites or six to eight steps, constraints that interact across them (a budget, a schedule), and one failure to recover from part-way. |
| impossible | The site's rules or stock make the request impossible. The right outcome: say so, give the site's reason, change nothing. |

The properties, as `levels.mjs` counts them:

| property | counted as |
| --- | --- |
| `sites`, `stepSites` | the sites the reference solution touches, in the order it meets them, and per step (the inbox is not a site) |
| `steps` | how many prompts |
| `reads`, `writes` | lookups (a search, a list, one entity, a quote) and changes the site keeps; signing up and in are neither |
| `named` | the target is named in the prompt |
| `constraints` | requirements the target is found by, besides the place and the date the prompt is about |
| `rule` | a site rule decides the outcome (a fee, the area a party fits, the size that serves the people): the outcome without it is another one |
| `tempting` | a tempting option fails one requirement: a cheaper fare whose carrier takes one bag, an earlier session that is full (checked live by the integrity tool) |
| `signUp` | the errand asks for a new account, confirmed with the code mailed to the inbox. The sign-in every write needs is not counted: it is the same in every task |
| `interacting` | requirements that span sites or steps decide each other (the night a flight lands decides the hotel's first night; the tickets decide what is left of a budget for the room); choosing each part on its own breaks them |
| `recovered` | a write the site refuses part-way, then one it makes: deterministic at the seed (the carrier takes one bag, the terrace seats fewer, the seat is taken) |
| `impossible` | the request is refused by the site's rules or stock, with the code the task names |

"One read or one write" admits a task with at most one of each (look the
named thing up, then book it). A task of one prompt on one site that is
found by two or three requirements, or whose outcome a rule decides, is
medium; "one site" is read per step, so a two-prompt plan with one site in
each can be medium too.

At seed 4242 the corpus holds 120 tasks: 30 easy, 30 medium, 40 hard (10 of
them very hard, in five areas) and 20 impossible, every area at every level
but easy in the two multistep areas, which have none by nature.
`cuj-tasks.md` has the table.

## What a state step's checks read

A state step's oracle is a list of checks (the verifier's spec format is in
`compose/specs/README.md`). They read the sites' rows through their REST API
and the sites' **change ledger**, which records, in the same transaction as
the write, every write made or refused (with the site's reason code and what
the request was about), every read of a single entity, and every step of
signing up and in, with the door it came through and who was signed in (the
README's *The change ledger*). Only the verifier reads it.

- **row**: a row is there that matches. With `entity`, the check reports when
  the row was last written (`at`), or, with `"at": "first"`, when it was made.
- **absent**: no row matches.
- **ledger**: an entry matches (any of a list of matchers), optionally
  `after` the entry an earlier check stood on. An entity or subject id
  `"@<check name>"` is the entity an earlier check stood on: the reservation a
  step-1 check found, so a step-3 check can ask for a change to that one.
- **unchanged**: the ledger holds no successful write in a scope (some sites;
  one entity, or the writes about one thing), optionally only `after` an
  earlier check's entry and `except` named writes.

How the corpus uses them:

- A booking made for a new person is a row check on that person's bookings
  (one, exactly, with the details asked), placed by its entity.
- A change or cancel names the booking's row, and holds the customer's other
  bookings to no write at all (`unchanged`), so a run that also cancelled the
  wrong one fails.
- Acting as yourself adds a ledger check that the write was made signed in as
  that person (`actor`); a sign-up adds one that the account was confirmed
  with its code.
- An impossible step is an `unchanged` check over what it names (the thing
  itself, and the writes about it) and a `ledger` check that the agent looked
  at it or was refused about it for the site's reason. A run that did nothing
  reads nothing and is refused nothing, and fails.
- In a task of several steps, each step's check stands on its own write: the
  step that made a booking by the booking's first write, a step that changed
  it by the first change of that booking after the step before's, so a change
  made in step 3 does not pass step 2. A step that asks for a value checks it
  in the final rows, which the later steps keep.

## The verifier's answer

```
POST /w/<id>/verify/v1/submit/cuj-<…>      → asked once, after the agent's last turn
```

```jsonc
{ "verdict": "OK",                         // OK only when every state step is OK
  "steps": [
    { "step": 1, "verdict": "OK", "checks": [ { "name": "booked", "passed": true, "at": "2027-03-01T10:02:11.482Z" } ] },
    { "step": 3, "verdict": "OK", "checks": [ { "name": "moved", "passed": true, "at": "2027-03-01T10:04:52.017Z" },
                                              { "name": "in the private room", "passed": true } ] } ],
  "details": [ … ] }
```

- `step` counts from 1, the task's own prompt. A `json` step is not listed:
  whoever holds the conversation grades that reply against its key. What is
  submitted therefore does not matter to a task of several steps.
- `at` is the time of the ledger entry or row write that satisfied the
  check: the site's own record, never the time of the submission. Placing each
  check in the turn its `at` falls in tells which step a change was made in.
  A check that says what did not happen (`absent`, `unchanged`), or that reads
  a value, has none.
- A step's check that stands on "the first change after the step before's"
  takes the earliest such change. A step that makes two changes of one kind to
  one booking moves the next step's anchor into its own turn, so a run is best
  placed by all of a step's checks together.
- The submission reads current state only and may be repeated.

## Rubrics

Each step's criteria are written per template and filled with the task's own
values. They judge what a check cannot, from the reply and the trace: that the
reply says truthfully what was done (it claims no booking that was not made,
and reports the one that was); that nothing was done that was not asked (no
second booking, nothing else changed, no extra account); for an impossible
step, that the reply says it could not be done and gives the site's reason;
and that the agent stayed on the sites the task names. The same criteria grade
every setup, so none names a tool, a route or a way of replying; none states a
value a check expects or a template has the agent find; and none asks for
anything the prompt rules out. The corpus tool refuses a template whose
criteria do.

## Integrity

```
node tools/intent-integrity.mjs --base http://localhost:8080 --scenario cuj-v1
```

proves the corpus against a live benchme, at the corpus seed, every task in one
fresh workspace: every task the verifier checks fails before anything is done,
and so does each of its state steps; then each task in turn, step by step,
runs its reference solution, and after each state step exactly the state steps
up to it pass, every `at` they report falling while their own step ran; each
json step's live answer is accepted by its key and a
perturbed one refused; each impossible task's attempt is refused with the code
it names; a tempting option is what its template says; the countable
properties the solution shows are the ones the template declares, so the level
they give is the task's; and once every solution has run, every check still
passes, still at a time its own step ran, and every key still matches: no task
undid another.
